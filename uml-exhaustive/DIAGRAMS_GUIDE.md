## 1. ما هو UML ولماذا نستخدم المخططات؟

**UML** (Unified Modeling Language) هو لغة قياسية عالمية لرسم مخططات توضيحية للبرمجيات.
لا يهم اللغة أو التقنية التي تكتب بها الكود — UML يتحدث عنها بلغة بصرية مفهومة للجميع.

### لماذا نستخدم المخططات في هذا المشروع؟

| السبب | التوضيح |
|---|---|
| **فهم النظام بسرعة** | مخطط واحد يغني عن صفحات من الوصف النصي |
| **التواصل بين الفريق** | المطور والمصمم والمدير يفهمون المخطط ذاته |
| **التوثيق الأكاديمي** | متطلبات التخرج تتطلب مخططات هندسة برمجيات |
| **اكتشاف الأخطاء مبكرًا** | رسم المخطط قبل الكود يكشف الثغرات التصميمية |
| **تتبع المتطلبات** | كل مخطط مرتبط بأرقام المتطلبات والكود الفعلي |

## 3. المخطط الأول: حالات الاستخدام (Use Case)

**الملف:** `01_use_case.puml`
**النوع:** PlantUML Use Case Diagram
**العدد:** 48 حالة استخدام + 4 فاعلين + 4 أنظمة خارجية

### ما هو هذا المخطط ويماذا يُظهر؟

مخطط حالات الاستخدام يجيب على سؤال واحد:
> **"من يفعل ماذا في النظام؟"**

يُظهر الفاعلين (الأشخاص أو الأنظمة الخارجة) والمهام (الحالة الاستخدامية) والعلاقات بينها.

### لماذا نستخدمه؟

- يُحدد نطاق النظام بالكامل (ما الذي يندرج تحته وما الذي لا يندرج)
- يُظهر صلاحيات كل دور (Admin يفعل X لكنه لا يفعل Y)
- يُشفّر قواعد RBAC (الوصول القائم على الأدوار)

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى في المخطط | مثال في проектنا |
|---|---|---|
| **المستطيل الخارجي** | حد النظام (System Boundary) — كل ما داخله هو جزء من EventFlow | مستطيل "EventFlow Platform" |
| **الممثل (Actor) `human icon`** | فاعل بشري يتواصل مع النظام | `Visitor`, `Attendee`, `Organizer`, `Admin` |
| **الممثل `<<system>>`** | نظام خارجي يتواصل مع النظام | `Supabase`, `LM Studio (محلي)` |
| **البيضة (Use Case `oval`)** | مهمة أو إجراء واحد يمكن تنفيذه | "UC01 Browse Published Events" |
| **السهم الأسود `-->`** | فاعل يؤدي حالة استخدام | Visitor → UC01 |
| **السهم المتقطع `..>` مع `<<include>>`** | خطوة إلزامية يجب أن تحدث مع الحالة الأصلية | التسجيل يشمل دائمًا توليد تذكرة QR |
| **السهم المتقطع `..>` مع `<<extend>>`** | خطوة اختيارية تحدث بشروط محددة | فعالية خاصة → تمديد بالتحقق من رمز الدعوة |
| **الأسهم الطويلة `<|--`** | تعميم (Inheritance) — الدور يرث صلاحيات الدور الأب | Admin ← Organizer ← Visitor |

### كيف تقرأ المخطط:

1. ابدأ من **الفاعل** (يسار المخطط)
2. تتبع **السهم** إلى **حالة الاستخدام** (بيضة)
3. راجع **العلاقات** (`include` = إلزامي، `extend` = شرطي)
4. اقرأ **الملاحظات** (مربعات صفراء) للسيناريوهات المغطاة

### العلاقة مع الكود:

| حالة استخدام | الملف في الكود |
|---|---|
| UC05 تسجيل الدخول | `src/services/authService.ts` → `login()` |
| UC10 تسجيل في فعالية | `src/services/eventService.ts` → `registerForEvent()` |
| UC25 فحص الدخول | `src/services/attendanceService.ts` → `checkIn()` |
| UC03 المساعد الذكي | `supabase/functions/chatbot/index.ts` |

## 4. المخطط الثاني: الفئات (Class Diagram)

**الملف:** `02_class.puml` (+ أجزاؤه: `02_class_entities.puml`, `02_class_services.puml`, `02_class_platform.puml`)
**النوع:** PlantUML Class Diagram
**العدد:** 29 كيان + 14 خدمة + 15 Enum + عناصر منصة

### ما هو هذا المخطط ويماذا يُظهر؟

مخطط الفئات يجيب على سؤالين:
> **"ما هي البيانات التي يتعامل معها النظام؟"** (الكيانات)
> **"كيف تتفاعل هذه البيانات مع بعضها؟"** (العلاقات والخدمات)

### لماذا نستخدمه؟

- يُحدد بنية البيانات لكل جدول في قاعدة البيانات
- يُظهرRelationships (علاقات) بين الكيانات (FK, One-to-Many, Many-to-Many)
- يُوثّق واجهات الخدمات (Methods) التي يستخدمها التطبيق
- يكشف عن الطبقات (Architecture Layers)

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى | مثال |
|---|---|---|
| **المربع `class`** | كيان أو فئة في النظام | `User`, `Event`, `Registration` |
| **`<<entity>>`** | كيان مرتبط بجدول في قاعدة البيانات | `Event`, `Ticket` |
| **`<<service>>`** | كائن خدمة (woo Commerce logic) | `AuthService`, `EventService` |
| **`<<context>>`** | سياق React (Provider) | `AuthContext` |
| `<<guard>>` | حارس مسار (Route Guard) | `ProtectedRoute` |
| **`<<singleton>>`** | كائن واحد مشترك (لا يُنشأ أكثر من مرة) | `supabaseClient` |
| **`<<edge_function>>`** | دالة Edge على Supabase (Deno) | `ChatbotEdgeFunction` |
| **الخطوط في المربع** | `+` = عام (public)، `-` = خاص (private) | `+ login(email, password)` |
| **السهم `-->`** | علاقة بين كيانين (FK) | `User --> Profile : owns` |
| **`1` و `0..*`** | العدد (multiplicity): واحد لعدة | `User "1" --> "0..*" DeviceSession` |

### الهيكل الطبقي في مخططنا:

```
┌─────────────────────────────────────────┐
│  طبقة العرض (Presentation)             │
│  AuthContext, ProtectedRoute, Pages     │
├─────────────────────────────────────────┤
│  طبقة الخدمات (Services)               │
│  AuthService, EventService, etc.        │
├─────────────────────────────────────────┤
│  طبقة البنية التحتية (Infrastructure)  │
│  supabaseClient, RateLimiter            │
├─────────────────────────────────────────┤
│  طبقة قاعدة البيانات (Database)        │
│  الكيانات: User, Event, Ticket, etc.    │
└─────────────────────────────────────────┘
```

### العلاقة مع الكود:

| الكيان/الخدمة | الملف في الكود |
|---|---|
| `User`, `Event`, `Ticket` | `src/types/index.ts` (تعريفات TypeScript) |
| `AuthService` | `src/services/authService.ts` |
| `EventService` | `src/services/eventService.ts` |

## 5. المخطط الثالث: العلاقات (ERD)

**الملف:** `03_erd.mmd`
**النوع:** Mermaid ER Diagram
**العدد:** 30 جدول + كل علاقة FK فعلية

### ما هو هذا المخطط ويماذا يُظهر؟

ERD (Entity Relationship Diagram) يجيب على سؤال:
> **"كيف تتخزن البيانات في قاعدة البيانات؟ وما هي العلاقات بين الجداول؟"**

### لماذا نستخدمه؟

- يُحدد هيكل قاعدة البيانات بالكامل (كل جدول وكل عمود)
- يُظهر العلاقات الفعلية (FK constraints) بين الجداول
- يكشف الجداول المغلقة أمام العميل (المؤمنة عبر RLS)
- المرجع الأساسي لمطوري Backend

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى | مثال |
|---|---|---|
| **`||--o{`** | واحد يتصل بعدة (One-to-Many) | `EVENTS ||--o{ SESSIONS` |
| **`||--o|`** | واحد يتصل بأحد اثنين (One-to-ZeroOrOne) | `REGISTRATIONS ||--o\| TICKETS` |
| **`PK`** | مفتاح أساسي (Primary Key) | `uuid id PK` |
| **`FK`** | مفتاح أجنبي (Foreign Key) | `event_id FK` |
| **`UK`** | فريد (Unique) | `email UK`, `unique_code UK` |
| **المربع** | جدول في PostgreSQL | `EVENTS { ... }` |
| **الخط داخل المربع** | عمود (Column) في الجدول | `text status "draft \| published \| archived"` |
| **التعليقات `%%`** | ملاحظات أمان وتوثيق | `%% password_hash: REVOKE ALL للعميل` |

### كيف تقرأ ERD:

1. ابدأ من **الجدول المركزي** (غالبًا `EVENTS` أو `USERS`)
2. تتبع **الأسهم** لمعرفة الجداول المرتبطة
3. اقرأ **الأعمدة** داخل كل جدول
4. راجع **التعليقات** للحقول المغلقة (الأمان)

### العلاقة مع الكود:

- **الحقيقة المطلقة:** `supabase/schema.sql` — هذا الملف هو مصدر الحقيقة الوحيد
- **المخطط يطابق** `src/types/index.ts` 1:1
- **RLS:** كل جدول يفرض صفوف أمان (Row Level Security)

## 6. مخططات التتابع (Sequence Diagrams)

**الملفات:**

- `04f_sequence_chatbot.mmd` — المساعد الذكي (LLM + Tool Calling)

**النوع:** Mermaid Sequence Diagram
**العدد:** 6 مخططات تتابع

### ما هو مخطط التتابع ويماذا يُظهر؟

مخطط التتابع يجيب على سؤال:
> **"كيف يتفاعل جزءان في النظام مع بعضها خطوة بخطوة؟"**

يُظهر **الرسائل المتبادلة** بين المشاركين (Objects) مرتبة زمنيًا.

### لماذا نستخدمه؟

- يُظهر تسلسل الأحداث بدقة (خطوة 1 ثم 2 ثم 3)
- يكشف نقاط الفشل المحتملة (`)alt` = بدائل)
- يُوثّق التفاصيل التقنية (RPC calls, DB queries, Error handling)
- المرجع الأهم لفهم كيف يعمل النظام فعليًا

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى | مثال |
|---|---|---|
| **المربع الرمادي `participant`** | مشارك (كائن أو خدمة أو قاعدة بيانات) | `U as المستخدم`, `DB as Supabase` |
| **السهم المنحني `->`** | رسالة من مشارك لآخر | `U->>A: login(email, password)` |
| **السهم المنحني المتقطع `-->>`** | رد (response) | `DB-->>S: JSON(user, profile)` |
| **`rect rgb(...)`** | صندوق يُجمّع سيناريو كاملًا | صندوق "1) تسجيل الدخول" |
| **`alt ... else`** | شرط (if/else) | نجاح vs فشل |
| **`loop`** | حلقة تكرارية | إعادة المحاولة (retry) |
| **`Note`** | ملاحظة توضيحية | "مسار Legacy عند PGRST202" |
| **`autonumber`** | ترقيم تلقائي للرسائل | 1, 2, 3, 4... |

### كيف تقرأ مخطط التتابع:

1. اقرأ **العنوان** أولاً (أي سيناريو؟)
2. ابدأ من **أعلى اليسار** (أول رسالة)
3. انتقل **لأسفل** خطوة بخطوة
4. عند `alt` = "إذا حدث كذا، وإلا حدث كذا"
5. عند `rect` = هذا سيناريو كامل منفصل

| `04a` Auth | `src/services/authService.ts`, `src/contexts/AuthContext.tsx`, `schema.sql` |

## 7. مخططا النشاط (Activity Diagrams)

**الملفات:**
- `05a_activity_registration.mmd` — نشاط التسجيل الشامل
- `05b_activity_checkin.mmd` — نشاط الدخول (Check-in)

**النوع:** Mermaid Flowchart (يُستخدم كـ Activity Diagram)
**العدد:** 2 مخططات

### ما هو مخطط النشاط ويماذا يُظهر؟ (البنية المعتمدة)

مخطط النشاط يجيب على سؤال:
> **"ما هي خطوات تنفيذ عملية، وما هي الشروط والحالات المتفرعة داخلها؟"**

> **⚠️ المبدأ البنيوي المعتمد (أصح):**
> **يبدأ المخطط بالنشاط الكبرى أولًا** (مثل "التسجيل في الفعالية" / "الدخول إلى الفعالية")،
> ثم **تُمثل الشروط والحالات داخل مسار النشاط كتحققات أثناء التنفيذ** — وليس العكس
> (أي لا تُعرض الشروط كبوابات قبل النشاط). هذا يجعل القراءة طبيعية: النشاط متقدّم
> والشروط تُفحص أثناء سير العملية، والمسارات الفرعية (فشل/بدائل) تنبثق منه.

### لماذا نستخدمه؟

- يُحدد كل سيناريو ممكن (نجاح + فشل + حدود)
- يكشف عن الثغرات في منطق الأعمال (Missing cases)
- يُستخدم كمرجع لكتابة Unit Tests

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى | مثال |
|---|---|---|
| **الدائرة `([start])`** | بداية النشاط الكبرى | `"النشاط: التسجيل في الفعالية"` |
| **المستطيل `[]`** | إجراء/نشاط (Action) | `"(النشاط) تجهيز طلب التسجيل"` |
| **الماسة `{}`** | شرط/حالة تُفحص أثناء النشاط | `"(أثناء الفتح) الفعالية منشورة؟"` |
| **السهم `-->`** | اتجاه التدفق | من النشاط إلى شرط داخل مساره |
| **الدائرة `([end])`** | نهاية النشاط | "إنهاء بفشل" / "إنهاء بنجاح" |
| **`subgraph`** | مجموعة إجراءات مرتبطة | "مسار الفعاليات أونلاين" |
| **اللون الأحمر** | فشل (Error) | "فشل التسجيل: «انتهى موعد التسجيل»" |
| **اللون الأخضر** | نجاح (Success) | "تم التسجيل — تذكرة جاهزة" |

### كيف تقرأ مخطط النشاط (البنية الصحيحة):

1. ابدأ **بالنشاط الكبرى** (الدائرة العلوية) — هذه هي العملية بأكملها
2. انتقل عبر **المستطيلات** (مراحل تنفيذ النشاط)
3. عند **الماسة** تحقّق من **الشرط داخل مسار النشاط** واختر المسار (نعم/لا)
4. الخروج من أي شرط ينبثق عنه مسار فرعي (فشل → أحمر، نجاح → أخضر)
5. انتهى إما بـ **نجاح** أو **فشل**

| المخطط | الملف المرجعي |
|---|---|
| `05a` Registration | `src/services/eventService.ts` → `registerForEvent()` |
| `05b` Check-in | `src/services/attendanceService.ts` → `checkIn()`, `findTicketByCode()` |

## 8. المخطط السادس: الهندسة المعمارية (Architecture)

**الملف:** `06_architecture.mmd`
**النوع:** Mermaid Flowchart (Layered Architecture)
**المصدر:** `package.json`, `src/**`, `supabase/`

### ما هو هذا المخطط ويماذا يُظهر؟

مخطط الهندسة المعمارية يجيب على سؤال:
> **"كيف يتكون النظام ككل؟ وما هي الطبقات والأدوات المستخدمة؟"**

يُظهر النظام كطبقات (layers) من أعلى (المستخدم) لأسفل (قاعدة البيانات).

### لماذا نستخدمه؟

- يُعطي صورة شاملة للنظام في مخطط واحد
- يُحدد التقنيات المستخدمة في كل طبقة
- يُظهر مسارات الاتصال (HTTPS, WSS, RPC)
- يكشف عن فصل المسؤوليات (Separation of Concerns)

### الأجزاء الأساسية وماذا تعني:

| الطبقة | المحتوى | اللون في المخطط |
|---|---|---|
| **طبقة العرض (Client)** | صفحات React + سياقات + حماية مسارات + QR | أزرق فاتح |
| **طبقة الخدمات (Services)** | Repository Pattern — كل خدمة مسؤولة عن مجال واحد | أخضر فاتح |
| **طبقة الواجهة الخلفية (Backend)** | PostgreSQL + RPCs + Realtime + Storage + Edge Functions | برتقالي فاتح |
| **أنظمة خارجية (External)** | LM Studio (خط الفعلي للروبوت) + البريد + الكاميرا + OpenRouter (مسار بديل غير مستخدم) | بنفسجي فاتح |

### العلاقة مع الكود:

- **الهيكل العام:** `package.json` (React 19 + Vite + Tailwind)
- **الطبقة الخلفية:** `supabase/schema.sql` + `supabase/functions/`
- **الاتصالات:** `src/lib/supabase.ts` (anon key + RLS)

## 9. المخطط السابع: آلة الحالات (State Machine)

**الملف:** `07_state_machine.mmd`
**النوع:** Mermaid State Diagram
**الكائنات:** تسجيل + تذكرة + حضور + فعالية + جلسة + تقييم + دعوة

### ما هو مخطط آلة الحالات ويماذا يُظهر؟

آلة الحالات تجيب على سؤال:
> **"ما هي الحالات التي يمكن أن يكون فيها الكائن؟ وما هي التحويلات المسموحة؟"**

### لماذا نستخدمه؟

- يُحدد فقط التحويلات المسموحة (يمنع الأخطاء)
- يكشف عن الحالة المحظورة (مثل: التسجيل من `cancelled` إلى `confirmed` غير مسموح)
- المرجع لكتابة Validation Rules

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى | مثال |
|---|---|---|
| **`[*]`** | نقطة البداية (Initial State) | `[*] --> Reg_waitlisted` |
| **النص المكتوب** | حالة (State) | `Reg_confirmed`, `T_valid` |
| **السهم `-->`** | انتقال (Transition) من حالة لأخرى | `Reg_confirmed --> Reg_cancelled` |
| **النص على السهم** | الشرط/المشغّل للانتقال | "capacity free / إدراج مباشر" |
| **`note right of`** | ملاحظة توضيحية | "آلة حالة التسجيل..." |

### الحالات الرئيسية في نظامنا:

| الكائن | الحالات | التحويلات المهمة |
|---|---|---|
| **التسجيل** | confirmed → cancelled / waitlisted → confirmed | الانتظار → ترقية عند إلغاء شخص آخر |
| **التذكرة** | valid → used / invalid | الدخول → التحول لـ "مستخدمة" |
| **الحضور** | None → CheckedIn → CheckedOut | فتح رابط الاجتماع → حضور تلقائي |
| **الفعالية** | draft → published → archived | النشر فقط بعد اكتمال التفاصيل |
| **الجلسة** | active → revoked | الخروج أو إعادة تعيين كلمة المرور |

## 10. المخطط الثامن: المكونات (Component)

**الملف:** `08_component.mmd`
**النوع:** Mermaid Flowchart (Component Style)
**المكونات:** عميل + خدمات + بنية تحتية + خلفية + أنظمة خارجية

### ما هو مخطط المكونات ويماذا يُظهر؟

مخطط المكونات يجيب على سؤال:
> **"ما هي الوحدات البرمجية المستقلة في النظام؟ وما هي الواجهات بينها؟"**

### لماذا نستخدمه؟

- يُفصل النظام إلى مكونات مستقلة (قابلة للاستبدال)
- يُحدد الاعتماديات الحقيقية (Import + Call)
- يكشف نقاط الاتصال (Ports/Interfaces)

### الأجزاء الأساسية وماذا تعني:

| الرمز | المعنى |
|---|---|
| **`subgraph`** | مجموعة مكونات مرتبطة (طبقة واحدة) |
| **النص داخل `subgraph`** | اسم المكون + وصفه |
| **السهم `-->`** | اعتمادية حقيقية (import / call) |
| **`---` على السهم** | واجهة (Interface / Port) |
| **النقاط المنقطة `-.->`** | اعتمادية اختيارية (fallback) |

### المكونات الرئيسية:

| المكون | المسؤولية |
|---|---|
| `PresentationLayer` | صفحات واجهة المستخدم |
| `AuthComponent` | المصادقة + RBAC |
| `ChatComponent` | الدردشة + المساعد |
| `QRScanner` | فحص التذاكر |
| `AuthServiceComponent` | RPC auth + rate limit |
| `EventManagementComponent` | CRUD الفعاليات |
| `RegistrationComponent` | التسجيل/الإلغاء/الدعوات |
| `AttendanceComponent` | الدخول/الخروج |
| `ChatServiceComponent` | قنوات + رسائل + Realtime |
| `EvaluationComponent` | الاستبيانات + التقييم |
| `DataAccessComponent` | SupabaseClient (REST/RPC) |
| `ChatbotFunction` | Edge Function بديل + OpenRouter (غير مستخدم في الواجهة الحالية) — المسار الفعلي: `useChat` → LM Studio محلي + REST مباشر |

## 11. المخطط التاسع: النشر (Deployment)

**الملف:** `09_deployment.mmd`
**النوع:** Mermaid Flowchart (Deployment Style)
**العُقد:** جهاز المستخدم + الاستضافة + Supabase Cloud + أنظمة خارجية

### ما هو مخطط النشر ويماذا يُظهر؟

مخطط النشر يجيب على سؤال:
> **"أين يعمل كل جزء من النظام؟ وكيف يتواصل العُقد مع بعضها؟"**

### لماذا نستخدمه؟

- يُحدد البنية التحتية للنشر (أين كل شيء يعمل)
- يُظهر بروتوكولات الاتصال (HTTPS, WSS, HTTP)
- يكشف عن نقاط الاتصال مع الأنظمة الخارجية

### العُقد الرئيسية:

| العقدة | الأداة/الخدمة | بروتوكول الاتصال |
|---|---|---|
| **جهاز المستخدم** | EventFlow SPA (Vite build) + كاميرا QR | — |
| **استضافة الملفات** | ملفات dist المبنية | HTTPS (تحميل SPA) |
| **Supabase Cloud** | PostgreSQL + Edge Functions + Realtime + Storage | HTTPS + WSS |
| **LM Studio** | خادم النموذج المحلي — المسار الفعلي للروبوت في الواجهة | HTTP محلي |
| **OpenRouter** | LLM API (بديل تصميمي عبر Edge Function غير مستخدم) | HTTPS (خادم فقط) |
| **Email Gateway** | توصيل روابط إعادة التعيين | SMTP (محاكى) |

### مسارات الاتصال المهمة:

```
المتصفح ──HTTPS──▶ Supabase (REST/RPC/Storage)
المتصفح ──WSS────▶ Supabase (Realtime)
المتصفح ──HTTP────▶ LM Studio (chat/completions) [المسار الفعلي للروبوت]
Edge Function ──HTTPS──▶ OpenRouter (LLM) [بديل تصميمي غير مستخدم]
Edge Function ──HTTPS──▶ PostgreSQL (service-role) [بديل تصميمي غير مستخدم]
```
